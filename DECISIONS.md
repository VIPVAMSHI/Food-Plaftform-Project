# Decisions

One or two lines each: what, and why. Newest last.

1. **Fastify, not Express.** Built-in JSON-schema/logging, `app.inject()` for fast in-process API tests, and it was already in place.
2. **`node:sqlite` (built into Node 22), not better-sqlite3.** _Superseded by #40 (libSQL)._ No native compile step on the deploy host, so `npm ci` cannot fail on a missing toolchain. Needs Node ≥ 22.13; the experimental warning is silenced with `--disable-warning=ExperimentalWarning`.
3. **68 places, not 35.** The owner chose to keep the 68-place dataset from the earlier session; every count in tests and preflight uses 68.
4. **The browser renders places from the bundled dataset; the server seeds its DB from the same file (`src/data/places.ts`).** _Server side superseded by #41: no seeding, places are served from memory._ _Server side superseded by #41: no seeding, places are served from memory._ One source of truth, and the list still renders if the API or wifi dies mid-demo. `GET /api/places` exists for the assistant and API clients.
5. **In-app "add an API key" prompt and "AI is off" banner are development-only.** On stage the audience must never see "AI is off"; on a public URL anyone could set the first key. Production (`npm start`) hides them and `POST /api/ai/key` returns 404. Override with `AI_KEY_PROMPT=on`.
6. **Env var `DB_PATH`** (brief's name) replaces the earlier `DATABASE_PATH`. _Superseded by #40: `DATABASE_URL` first; `DB_PATH` still works (render.yaml)._
7. **No hardcoded model.** `LLM_MODEL` is required whenever `LLM_API_KEY` is set; startup fails with a clear message otherwise. `.env.example` suggests `claude-haiku-4-5` (fast, inexpensive).
8. **Past dates:** new plans must be today or later in Seattle time; an edit cannot move a plan into the past. Existing past plans can still be viewed and deleted. The UI date inputs use the same `min`.
9. **Duplicates:** one plan per (user, place, date). A second one returns 409 and the UI says "already planned for that day". The old behaviour (silently overwriting the other date) was data loss.
10. **Assistant rate limit degrades instead of refusing.** Over the per-IP LLM budget, answers come from the cache or local matcher (`source` says which) instead of a 429, so the audience never sees a refusal. A hard ceiling (429 with a friendly message) protects the server from floods; the front end falls back locally on it.
11. _Superseded by #41._ **Places are upserted on every boot** (insert or update by id, never delete). This is idempotent, keeps foreign keys from plans intact, and picks up dataset edits.
12. **Coordinates from OpenStreetMap Nominatim** for all 68 addresses (6 needed a simplified address; all checked against Seattle bounds and their neighborhood). Used only for "sort by my location"; travel estimates still come from the listed miles.
13. **A time limit means door to table: travel + estimated wait.** "I have 30 minutes" is about when you eat, not when you arrive. The chip reads "≤ N min total" so the meaning is visible.
14. **If the model returns no usable picks but code found matches, answer locally.** An empty answer would look like a bug on stage. `meta.llmError` records it.
15. **The 6 s LLM deadline covers the retry.** One retry on 429/5xx/network only if ≥ 750 ms remain, so the worst case is ~6 s, never 12 s.
16. **A 401/403 from the provider disables the key in memory until restart** (`markRejected`). Every later request falls back instantly instead of waiting on a doomed call. The env file is never edited by an error.
17. **Reply text is composed in code (English); the model only picks ids and writes the one-line reasons.** Keeps counts, names, and limits in the reply exactly right. Reasons follow the request language.
18. **Fonts self-hosted via @fontsource** (DM Sans, Playfair Display). No Google Fonts request, so venue wifi or a strict CSP cannot change the look; system fonts are the fallback.
19. **Colors darkened for contrast:** coral text #f06a4f → #b9432a (3.0 → 5.4:1 on white), muted #77837d → #5f6b66, nav grey → #5f6b66. Minimum font size 11 px. Same palette, readable on a projector.
20. **Projector scaling:** at ≥ 1600×1000 the phone frame is zoomed 1.2× (1.5× at ≥ 2400×1300) instead of shrinking text.
21. **Labels:** "Customization" → "Ask the food assistant"; "YOUR LOCATION" → "YOUR AREA" (it is a filter, not GPS); the date chip reads "Plan date". The demo profile name stays "Alex Morgan" (one constant, `DEMO_USER`), with "Demo profile. There is no sign-in in this version."
22. **Local cache entries are rebuilt on every boot; only live-model entries persist.** Local answers are cheap and deterministic, so a code or data change can never leave a stale cached answer on stage.
23. **Photos recompressed to ≤ 720 px wide** (2.9 MB → 1.2 MB total, largest 89 KB). They render at ≤ 400 CSS px.
24. **Demo queries chosen from the eval run** (`server/src/assistant/demoQueries.ts`): each returns three picks locally. "brunch in Fremont" (0 picks) and "seafood in Pike Place" (1 pick) were dropped. "sushi under $5 in Ballard" stays on purpose to show the honest "nothing fits" answer.
25. **Plain `.mjs` for preflight and the dist secret scan,** so they run on any Node 22 with no build or TypeScript loader, including from a laptop backstage against the deployed URL.
26. **Filters the assistant sets belong to that answer only.** Before, "cheap ramen near Capitol Hill" left Capitol Hill and $30 applied, so the next question ("I have 30 minutes") was silently narrowed. Each new answer now replaces the previous answer's area/budget/preference/time; filters the user picked stay. Found by the e2e demo-path test.
27. **"Other upcoming plans" list under the Plans day view.** After a reload the calendar shows today, so a plan on another day looked lost. The list (max 5, tap to jump to that day) keeps every saved plan one tap away. No new data or endpoints.
28. **The plan dialog suggests a time** (09:00 / 12:30 / 19:00 by Seattle meal moment) instead of starting empty. One less step on stage, and Safari's 12-hour time field no longer blocks keyboard users.
29. **Accessible names include the visible text** (WCAG 2.5.3): the header avatar, area button, search "GO", assistant header, chat picks, and calendar day initials (now drawn with CSS) were fixed after axe flagged them.
30. **Render** for hosting (see DEPLOY.md): Blueprint file, HTTPS, health check, secret prompt, Shell for reset, persistent disk on Starter. Free tier works with ephemeral data and cold starts (documented).
31. **Lighthouse bars:** performance ≥ 80 mobile / ≥ 90 desktop; accessibility ≥ 95; best practices ≥ 90; SEO ≥ 90. The brief's exact targets were not available after a context reset, so these were chosen and recorded here.
32. **Soak = 10 consecutive runs of unit + API tests and the full Chromium e2e suite** (`npm run test:soak`), stopping at the first failure.
33. **Chaos burst uses 100 concurrent connections.** 300 simultaneous connects hit macOS's pending-connection cap (`kern.ipc.somaxconn` = 128) and 1 of 300 was reset by the kernel; that measured the laptop, not the server. Linux hosts default to 4096.
34. **`postinstall` runs `npm ci` in `server/`,** so a clean install uses the exact server lockfile.
35. **FINAL_REPORT.md sections** (the brief's exact headings were lost in a context reset): status, what changed, test evidence, not run, deploy, risks, manual checklist, refactor ideas.
36. **The assistant uses Google Gemini, not Anthropic (requested).** `server/src/llm/google.ts` replaces the Anthropic client behind the same `LlmProvider` interface, so the assistant logic, cache and fallbacks are unchanged. Details: the key goes in the `x-goog-api-key` header (never the URL); Google reports a bad key as HTTP 400 `API_KEY_INVALID`, so that body is read to detect rejection; `maxOutputTokens` gets 1,024 tokens of headroom because Gemini counts thinking tokens against it; JSON mode is on. The key format check is loose (`shared/llm-key.ts`) because Google is introducing new key types: it only rejects typos and `sk-` keys from other vendors, and Google's own check decides validity. Default model `gemini-2.5-flash-lite` (thinking off by default, so it fits the 6 s deadline). `LLM_PROVIDER` is now `google` only; an old `anthropic` value stops startup with a clear message. NOT RUN against the real Google API (no key here): covered by a fake Gemini server in the API tests.
37. **Shutdown drops leftover connections after 1.5 s.** A browser holding a half-finished request made `SIGTERM` wait the full 10 s and exit 1 ("Shutdown took too long"), slowing a restart on stage. Requests get 1.5 s to finish, then `closeAllConnections()`; exit is 0. Found by reading two old server logs, reproduced by a new chaos check.
38. **Not pushed.** `git push -u origin demo-final` needs GitHub credentials that this machine doesn't have. The branch and tag are local; DEPLOY.md step 1 is the push.

## Vercel (branch `vercel-ready`)

Vercel docs checked on 2026-11-24 (vercel.com/docs): Functions duration limits, Node.js runtime and supported versions, Fastify on Vercel, project configuration (`vercel.json` rewrites/headers/functions), Vite SPA rewrites, environment variables, Deployment Protection, request headers (`x-forwarded-for`), CLI (`vercel build`, `link`, `env add`, `deploy --prod`). What each decision relies on is named in it.

39. **The whole Fastify API is one Vercel Function** (`api/index.ts` → `server/src/vercel.ts`), reached through the rewrite `/api/:path*` → `/api`. Docs: the Node.js runtime page recommends one function plus rewrites for a framework router, and the Fastify page says a Fastify app becomes a single function. Same routes, validation and error shape as the local server; no handler code is duplicated. The function restores `/api/<path>` from Vercel's `/api?path=` form before Fastify routes it.
40. **Database: libSQL via `@libsql/client` (Turso in production, `file:` locally and in tests).** Vercel's filesystem is read-only and `/tmp` is per instance, so the SQLite file could not hold shared data. Remote URLs use `@libsql/client/web` (HTTP only, no native code); `file:` uses the default entry, which needs the native `libsql` addon. `vercel.json` excludes that addon from the function bundle (verified: no `.node` files in `vercel build` output) and the function refuses `file:` URLs with a clear health error. Settings: `DATABASE_URL`, `DATABASE_AUTH_TOKEN`; `DB_PATH` still works when `DATABASE_URL` is empty, so render.yaml and DEPLOY.md are unchanged.
41. **Places are served from the bundled dataset (`server/src/places.ts`), not the database.** They never change at runtime, so there is nothing to seed, no write on cold start, and places, search and the assistant keep working when the database is down. Plans no longer have a foreign key to a places table; the API checks the id against the dataset.
42. **Schema changes only through `npm run db:migrate`** (`server/scripts/migrate.ts`, idempotent, numbered migrations in `schema_version`). The Vercel function never creates tables: it checks the version once per instance and reports `databaseSchema: false` in /api/health until the migration has run. The local server still migrates its own `file:` database on boot, so `npm start` works offline with no extra step. Old `bite.db` files from the previous release upgrade in place (tested).
43. **Configuration problems never crash the function** (`loadEnvLenient`): an invalid value is dropped, its default applies, and its name (never its value) is listed in `/api/health` `configProblems`. A key without a model turns the live model off instead of failing. The local server keeps the strict check that stops with a readable message.
44. **Env is read on the first request of each function instance, not at import.** Docs: env changes apply only to new deployments, so every request of a deployment would read the same values; reading per request would only repeat work. In practice this is "read at request time".
45. **Per-browser data via an anonymous id** (`src/state/clientId.ts`): a random UUID in localStorage, sent as `X-Client-Id` on every API call; the server validates it as a UUID (versions 1–8) and uses it as `user_id`. Not a login (the `TODO(auth)` markers stay). Missing or invalid id on plans/favorites → 400 `CLIENT_ID_REQUIRED`. If storage is blocked (some private modes) the id lasts for the page load. Plans saved under the old shared `demo-user` stay in that database but are not shown to anyone.
46. **Abuse limits are per browser, with a per-IP ceiling** (`VisitorLimiter`). On a public URL a whole room on venue Wi-Fi shares one IP, so per-IP limits alone let one busy table cut everyone else off. Found by running the demo path 10× against the local Vercel build: 120 assistant 429s from the old 40/min per-IP limit. Requests without an id count as one browser per IP. Numbers: request body 32 KB (unchanged); 50 plans per visitor, enforced atomically in the INSERT so parallel requests cannot pass it; plan/favorite changes 60/min per browser, 600 per IP (`WRITES_PER_MINUTE` changes the per-browser number); assistant requests 40/min per browser, 400 per IP (then a friendly 429 and the browser answers locally); live-model calls 15/min per browser, 60 per IP (then cache or local answers, no error; the lower IP multiple keeps model cost bounded).
47. **Rate limiters are per function instance** (in memory). Docs: Fluid compute reuses instances, but a burst can spread across several, so the limits are approximate on Vercel; good enough to stop a runaway script, not a determined attacker. A shared store (e.g. Upstash) would be the next step; not added (no new services).
48. **Client IP behind Vercel:** Docs: Vercel overwrites `x-forwarded-for` with the real client IP, so a client cannot spoof it. Fastify `trustProxy` is on in production, so `request.ip` is that address. Same on Render.
49. **`maxDuration: 15` s** for the function. Docs: Hobby and Pro allow far more (300 s default with Fluid compute), so 15 is a ceiling we chose: the LLM deadline is 6 s including the retry, then cache or local answer in milliseconds, and the browser gives up at 9 s and answers locally. 15 s leaves room for a cold start plus a slow database call without letting a stuck request run for minutes.
50. **Demo cache bundled as a TypeScript module** (`server/src/assistant/demoCache.ts`, written by `npm run cache:build`), not a JSON file read from disk. Every bundler includes an imported module; a file read at runtime would need `includeFiles` and path guessing. Live-model answers are kept in memory per instance on Vercel (read-only disk); the local server still persists them to `CACHE_PATH`. Without a key the script writes an empty cache, and answers come from the local matcher as before.
51. **Node 22 pinned (`engines: ^22.13.0`).** Docs: Vercel offers 22.x, 24.x and 26.x (default); `>=22` would select 26.x. 22 is what every test here ran on.
52. **Security headers on Vercel come from `vercel.json`** (same CSP as helmet, plus nosniff, Referrer-Policy, frame and cross-origin policies, HSTS, Permissions-Policy): static files are served by Vercel's CDN, not Fastify, so helmet only covers `/api`. `/assets/*` is cached as immutable (hashed names).
53. **SPA fallback by rewrite, excluding `/api` and anything with a file extension.** Docs: the filesystem wins over rewrites, so real files are served first; deep links like `/plans` get `index.html`; a missing `/photo.png` stays a 404 instead of returning HTML. Unknown `/api/*` paths reach Fastify, which answers a JSON 404.
54. **ESM imports in server-reachable code carry `.js` extensions.** Vercel runs the function as Node ESM, where `./travel` (no extension) fails to load. Found by running the built function locally; `tests/unit/esm-imports.test.ts` keeps it from coming back.
55. **Local Vercel check without an account:** `vercel build` (works offline with a local `.vercel/project.json`) plus `scripts/vercel-local.mjs`, which serves `.vercel/output` with Vercel's routing order (headers, filesystem, rewrites, function), and `sqld` (libSQL server) as a local Turso. It is an emulation; the real Preview deployment is still the proof.
56. **Vercel's Node helpers stay on (the default).** Read in `@vercel/node` 32: with helpers, Vercel reads the whole request body before the function runs, then replays it to `data`/`end` listeners. Fastify reads bodies only through those listeners (checked in its `content-type-parser.js`), so POST/PATCH work. Turning helpers off would need a `NODEJS_HELPERS=0` project variable, one more manual step. `scripts/vercel-local.mjs` reproduces the read-and-replay, and every e2e write ran through it. To be confirmed on the real Preview.
